# Команды откликов

Следующий этап после PR #3 переводит `POST /api/service`, action `application`, на существующий RPC `apply_workspace_command`. API отправляет только ревизию и команду; SQL читает состояние под общей с legacy writer блокировкой владельца. Возвращается snapshot той же транзакции с `revision + 1`.

## Контракт

| Поле команды | Создание | Обновление |
| --- | --- | --- |
| `action` | `application` | `application` |
| `id` | Отсутствует; SQL генерирует UUID | Строковый ID собственного отклика, 1–100 знаков |
| `title` | Обязателен, 1–300 знаков | В SQL-команде запрещён; прежнее название сохраняется |
| `status` | Один из семи статусов трекера | Один из семи статусов трекера |
| `note` | Строка до 3000 знаков | Строка до 3000 знаков |
| `resumeVersionId` | Собственный строковый ID версии или null; отсутствие даёт null | Собственный строковый ID версии, null снимает привязку; отсутствие сохраняет прежнее значение/отсутствие |

HTTP-маршрут нормализует отсутствующую заметку в пустую строку, как прежде. На прямом RPC поле `note` обязательно. Пустой или null `id` отклоняется, а не превращает обновление в создание. Строковые ID старых сохранённых версий поддерживаются; тип UUID не требуется для ссылки на уже существующую версию.

HTTP-маршрут отбирает допустимые поля намерения. Как и прежний API, он игнорирует `title` при обновлении и не принимает даты, историю или массив откликов от клиента. Прямой RPC отклоняет неизвестные поля. Новый ID при создании и все даты новых событий формирует БД. Ранее сохранённые ID, дата создания, название, события и неизвестные поля совместимости не меняются.

Смена статуса добавляет ровно одно событие. Правка заметки или привязки без смены статуса не создаёт события. Лимиты: 500 откликов, 200 событий на отклик. На пределе событий разрешены заметки и привязки; дальнейшая смена статуса отклоняется целиком.

## Граница записи

Сессия, `auth.uid()` и ревизия проверяются в существующем публичном RPC. Вспомогательная `private.apply_application_intent` — преобразование состояния с `SECURITY INVOKER`, пустым search_path и без EXECUTE для public/anon/authenticated. Она получает только snapshot, выбранный RPC по текущему владельцу. Новых таблиц и политик RLS нет.

Проверка команд не заменяет прежний commit gate: он продолжает проверять допустимый переход, записывать аудит и обновлять реляционную проекцию в той же транзакции. Чужая/отсутствующая версия, чужой отклик, неверная ревизия и превышение лимита не сохраняют частичных данных. Конфликт и неоднозначный сетевой сбой не вызывают повторную запись или fallback на snapshot.

## Миграция и откат

1. База должна содержать все предыдущие миграции, включая `20261028110000_workspace_commands.sql`.
2. Применить `20261028110001_application_commands.sql` до нового API-кода.
3. Проверить SQL-suite в изолированной тестовой базе и сценарий трекера с тестовым аккаунтом перед выпуском.

При откате API прежний `save_workspace` остаётся совместимым; новую SQL-функцию можно оставить. Снимать SQL-расширение при работающем новом API нельзя: команда `application` тогда перестанет поддерживаться. Для чистой установки `supabase/schema.sql` содержит обе стадии RPC и новую миграцию.

Дублирующие JSON-массивы пока сохраняются. Команды import/fact/version/restore, проверка паритета и удаление snapshot — отдельные задачи. Этот этап не меняет действующую базу до отдельного выпуска и не закрывает SMTP, restore провайдера или живую модель.
