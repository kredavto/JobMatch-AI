# Authentication shell and mail-form localization

Prepared after PR #25. Typed RU/EN copy covers the sign-in hero/consent/links, sidebar/header/footer, reauthentication and saved-server-text comparison, confirmation form and all recovery stages/feedback. These components accept the prepared locale prop; production page wrappers still use default RU. No public English route, query/cookie switch or partial language selector is introduced.

The consent text translates the existing installation statement. It does not establish legal approval of the operator’s hosting, location, retention or backup policies. That acceptance remains open. Source values, credentials, profile/vacancy/goal text, canonical actions/IDs/revisions and boolean consent remain unchanged. Quoted server texts use unknown-content lang. Locale is never added to auth API bodies.

Confirmation retains only status/boolean feedback, and recovery retains a static error key or status+stage plus a success key. The current locale resolves these at render, including late responses. Locale changes do not reset fields, PKCE stage/code, cooldown, request state or HTTP-based handling, and never resend or repeat an exchange/update. `mailFailure` retains default RU and its prior status/stage priority:429 remains rate-limit feedback; uncertain update outcomes advise trying the new password first. A changed password does not imply that other sessions were revoked: missing/false sessionsRevoked keeps the separate warning in either language. No provider diagnostics, raw response text or tokens become UI copy.

Recovery now has a synchronous pending ref in addition to its disabled button. Both forms ignore late UI results after unmount. In particular, confirmation can no longer create a fresh detached minute timer when its response arrives after leaving the form; existing cooldown timers are cleared on unmount. These are **UI lifecycle guards**, not network cancellation: an already submitted provider request/cookies may still complete. Navigation or locale change is not evidence that an email/password operation was cancelled. There are no automatic retries.

Mobile visual review separated the formerly adjacent password-recovery and confirmation links into vertical links with44px targets; both destinations are unchanged. English confirmation/recovery/login screenshots were inspected. This complements automatic axe/no-overflow checks; it is not a complete manual screen-reader or device audit.

Verification uses actual React forms/shell in ephemeral loopback fixtures with the existing pinned dev-only esbuild. Next Link is imported from the actual package; the fixture has an empty process.env configuration and no real Next router context. It verifies href/copy/form behavior, not full English Next navigation. Synthetic API responses intercept all email/exchange/update actions. Fake time verifies that changing locale does not restart success/429 cooldown or send a request at expiry. A mounted/unmounted timer observer verifies that a held confirmation response creates no detached60s timer after unmount. Recovery scenarios verify explicit exchange, cleared URL/code, password drafts, mismatch, late503 uncertainty, cleared password fields and partial-session warning. Shell scenarios verify credentials/consent, original owner/revision and preserved drafts after reauthentication and comparison. Russian production app regression exercises the actual Next routes and prior a11y/keyboard/offline/error/owner behavior.
