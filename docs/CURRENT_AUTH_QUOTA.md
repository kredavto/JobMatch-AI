# Current signed pre-auth quota: optional, not deployed

This proposal adapts the existing #17/#18/#40 design onto current unmerged #75 (saved letters, patched dependencies and source profile), without importing its old UI/migration stack or treating old CI as current proof. Fresh main `a3a9ef0c69e1e760010fc391234d66cd4a747e3b`, four plans and 68 open PRs were read first. Default `JOBMATCH_AUTH_QUOTA_MODE=local` retains per-process guards; those email keys now use a process-random HMAC. Local counters are not distributed protection.

`required` consumes signed PostgreSQL quota before login/register/refresh, recovery request/exchange/update and signup resend. Registration charges credentials and shared mail before signup; signup/recover/resend share normalized email. Passwords never become subjects; tokens/verifiers are HMACed locally. Origin/input/consent/cookie/local limits and mail-origin checks, where applicable, precede the central call. Invalid config/key/mode, malformed/unavailable RPC and denial do not fall back or invoke Auth/create cookies. Boolean false yields429/Retry-After60; config/RPC failure gives fixed503 `AUTH_PROTECTION_UNAVAILABLE`. Current Russian UI copy is preserved; this slice does not claim full RU/EN localization.

Only scope, HMAC pseudonym, epoch seconds and signature cross the fixed RPC. Its transport has a two-second total header/body deadline, 128-byte response cap, fatal UTF8, HTTP200/application-json/boolean requirements, no redirect and no retry. No client-supplied endpoint, quota or signing key is accepted. Provider diagnostics/error bodies are not displayed. Other existing Supabase operations retain their previous transport behavior; this bounded branch specifically protects pre-auth quota. Publishable apikey is sufficient; no service-role credential is introduced.

The separate32-byte server-only key is 64 lowercase hex in `JOBMATCH_AUTH_QUOTA_SECRET` and protected `private.auth_quota_config.signing_key`. Migrations seed no key. Subject HMAC message is `jobmatch-auth-subject-v1\n{scope}\n{normalized subject}`; signature message is `jobmatch-auth-quota-v1\n{scope}\n{subjectHex}\n{integerEpochSeconds}`. Both use HMAC-SHA256. DB accepts <=30-second age/<=5-second future skew, requiring synchronized clocks. Replay within that bound can only consume allowance, never authorize Auth or enlarge limits. Do not log RPC parameters; pseudonyms are linkable personal data, not anonymous data.

The global row serializes instances and charges subject-denied attempts; global refusal allocates no subject row. SQL errors roll back the whole operation. Fixed windows allow a boundary burst of up to two windows; stricter process-local limits may refuse earlier. These are starting policies, not proven capacity. A targeted attacker can exhaust an address/global budget, aliases vary, and quota refusal may expose recent activity for guessed identities. WAF/CAPTCHA, trusted ingress, direct Supabase Auth protection, password compromise controls and live capacity remain separate OPEN gates.

The narrow `public.consume_auth_quota` SECURITY DEFINER is intentional: pre-auth has no uid. It verifies shape/time/keyed MAC before any write, charges only fixed counters and returns only boolean. It cannot perform Auth, read profiles, mint sessions or configure keys. Empty search_path, qualified names,2s lock timeout, explicit revoke PUBLIC execute and explicit anon/authenticated execute; private tables have RLS/no policies and no public/anon/authenticated grants. user_metadata/JWT claims confer no authority. Requires pgcrypto in extensions; it refuses relocating an existing provider extension. Existing migration filenames and contents are preserved byte-for-byte. Consolidated schema appends exactly both migrations; native profile drill retains its pinned 15-table predecessor check, applies the exact known quota suffix to the populated upgrade path and tests the full current schema.

Three private tables hold config/counters/aggregate outcomes. Status/purge are fixed administrative private-schema operations via `scripts/auth_quota_ops.py`, no HTTP route or public RPC. Status reports aggregate counts only; strict shape/number/scope validation rejects secrets/extras, and purge is bounded1..1000 per table with SKIP LOCKED, separate explicit operator switches. Lazy expiry removes at most200 counters older than24h per authenticated signed quota call; it is not a strict retention SLA. No scheduler/purge was installed against user data. Provision an approved purge/monitoring/storage/PD retention process before activation.

The17-table application backup manifest intentionally excludes these three private tables and signing keys. An unrestricted DB dump may include them: restrict backup access, secure private material and rekey a provider restore before enabling traffic. Application fingerprint agreement does not verify quota secret backup. Existing synthetic letter/source17-table restore is not Supabase provider-copy restore/RPO/RTO.

Operator rollout (not performed): review current additive migration on an isolated approved provider copy, inspect inherited default privileges/RLS/advisors and actual signed anonymous PostgREST behavior, provision a distinct server/DB key through the approved secret process, validate trusted ingress/direct Auth controls, then approve enabling required and capacity/retention/outage behavior. Single-key rotation needs coordinated server/DB update and controlled interruption; mismatch closes access. Disabling required or rolling back code removes this application protection and is an explicit operator decision. Keep additive data/config unless a separate reviewed cleanup is approved.
