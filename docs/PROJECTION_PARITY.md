# Проверка паритета snapshot и нормализованных данных

Этап зависит от PR #6. Миграция `20261028110004_projection_parity.sql` добавляет только административную функцию `private.workspace_projection_report()`. Она не исправляет данные, не меняет приложение и не удаляет JSON-массивы.

## Выполнение

После применения миграции используйте Python 3, psql и административное подключение с чтением всех строк пяти прикладных таблиц. Подключение задаётся стандартными PG-переменными, PGSERVICE и защищённым .pgpass; пароли в аргументы не передаются.

```sh
PGSERVICE=jobmatch_restored python3 scripts/check_projection_parity.py
```

CLI выполняет одну REPEATABLE READ READ ONLY транзакцию с таймаутом и row_security=off. Функция SECURITY INVOKER дополнительно требует полный SELECT без активного RLS на каждой таблице, иначе выдаёт PARITY_SCOPE. PUBLIC/anon/authenticated не имеют EXECUTE; новым публичным RPC функция не является. Отдельной ограниченной роли не достаточно вручную выдать EXECUTE: неполный охват не должен превращаться в успешный отчёт.

Stdout содержит только JSON фиксированной схемы: format `jobmatch-projection-parity-v1`, checked, mismatches и ok. В нём нет владельцев, UUID, текста резюме/вакансии/заметок, строк свидетельств или хешей содержимого. Вывод psql и ошибки БД не пересылаются пользователю при неверном протоколе. После COMMIT ожидается отдельный маркер завершения; частичный вывод, сбой или таймаут означают ошибку проверки.

| Код выхода | Значение |
| --- | --- |
| 0 | Все счётчики mismatches равны нулю |
| 1 | Есть расхождения; данные не изменены |
| 2 | Проверка не завершена: клиент/подключение/права/миграция/формат/таймаут |

Checked сообщает число строк workspaces, profile_facts, resume_versions, applications и application_events. Пустая база может иметь ok=true с нулевым охватом; это не приёмка непустых данных.

## Что считается расхождением

| Счётчик | Что проверяется |
| --- | --- |
| facts | JSON-факты workspace отличаются от сборки profile_facts |
| versions | JSON-версии отличаются от resume_versions, включая исторические/неизвестные поля |
| applications | Отклики, события, порядок, null/absence связи отличаются от таблиц |
| payload_rows | Payload или три дублирующих массива имеют неверный/отсутствующий тип |
| position_rows | Позиции не образуют плотную последовательность с единицы для владельца/отклика |
| extra_rows | Extra не объект либо содержит зарезервированный ключ, который сборка JSON может скрыть |
| link_rows | Скрытая связь при отсутствующем поле либо недействительная ссылка на собственную версию |
| orphan_rows | Нормализованная строка не имеет своего родителя workspace/отклика |

Одна ошибка может увеличить несколько счётчиков; их сумма не является числом уникальных повреждённых строк. Сравнение сохраняет порядок, optional/unknown fields и различие отсутствующей resumeVersionId и явного null. Нулевые счётчики подтверждают равенство представлений в данном снимке, а не истинность фактов, релевантность Score или исправность SMTP/Auth.

## CI и диагностика

Synthetic restore drill создаёт три отдельные базы: чистую из schema.sql, восстановленную из её pg_dump и установленную последовательными миграциями. Он проверяет parity CLI до/после restore, в текущей зависимой ветке запускает десять SQL-suite на восстановленной и мигрированной базах, затем намеренно меняет строку. Одинаковое число записей не должно скрыть повреждение: manifest compare и parity CLI должны вернуть 1. Тестовые базы удаляются в finally.

При расхождении не запускайте автоматическое исправление по одному из представлений. Зафиксируйте результат и отдельно выясните источник истины в согласованной защищённой среде. Здесь нет команды repair и нет исключения отдельных ошибок из итогового ok.

## Перед удалением массивов

В исходном этапе PR #7 команды/commit строят прежнее состояние из payload. Следующая зависимая ветка переключает прежнее состояние и сравнения триггеров на таблицы (docs/CANONICAL_WORKSPACE_READS.md), сохраняя новые входы через NEW.payload и полный JSON snapshot. Следующий этап (docs/EXPLICIT_WORKSPACE_WRITES.md) переносит эти входы в явную commit-транзакцию и удаляет payload-триггеры, сохраняя сами массивы. Удалять массивы после одного успешного preflight нельзя.

Для следующего этапа нужно переключить эти пути на нормализованный источник, проверить старых/новых writers, аудит и историю, подготовить совместимый rollback и провести cutover под контролем всех записей. Итоговый preflight должен быть связан с самим cutover, иначе между проверкой и изменением возможна новая запись. После изменения режима хранения checker/формат и тесты должны быть обновлены; v1 предназначен для фазы с дублирующими массивами и не является постмиграционной проверкой нового режима.

Отчёт не заменяет восстановление настоящей копии провайдера, живую многоаккаунтную приёмку или разрешение на выпуск зависимых PR.

Следующая compact-ветка добавляет storage-v2 и явный --expect-format; это структурная проверка без сравнения значений с удалённым mirror. Для сохранности значений используется отдельный logical manifest. Контракт перехода/rollback: docs/COMPACT_WORKSPACE_STORAGE.md. Описание v1 выше остаётся действительным для mirror-фазы.
