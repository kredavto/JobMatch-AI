# Нормализованный источник прежнего состояния

Этап зависит от PR #7. Миграция `20261028110005_canonical_workspace_reads.sql` переводит чтение прежнего состояния для команд, legacy commit и сравнения в триггерах на нормализованные таблицы. Полный JSON snapshot сохраняется в `workspaces.payload`; новые данные по-прежнему передаются триггерам через NEW.payload. Удаление массивов этим этапом не разрешено.

## Граница записи

Закрытая `private.locked_workspace(revision)` проверяет владельца и активную сессию, берёт прежнюю транзакционную advisory-блокировку владельца и блокировку строки workspace, затем сверяет ревизию. Она собирает состояние через `read_workspace()` из profile_facts, resume_versions, applications и application_events, сохраняя скалярные/неизвестные поля payload. Для нового workspace возвращаются прежние пустые значения.

До любого изменения сравниваются все три массива с совместимым JSON-зеркалом. Дополнительно проверяются плотные позиции, тип/зарезервированные поля extra и скрытая связь с версией. При расхождении вызывается PROJECTION_CONFLICT; ни command RPC, ни legacy writer не исправляют данные автоматически. Устаревшая ревизия по-прежнему даёт CONFLICT до проверки паритета. Проверка ограничена текущим владельцем: повреждение чужого профиля не блокирует здоровый профиль.

HTTP-обёртка отображает PROJECTION_CONFLICT в 503 с безопасным сообщением без деталей БД. Повторной записи или fallback нет. Прямой RPC сохраняет обычный формат ошибки PostgREST. Исправление расхождения требует отдельного разбора источника истины администратором.

Команды и `private.commit_workspace` используют общий helper. Проверка commit повторяется под той же транзакционной блокировкой; старый save_workspace совместим с новыми ревизиями, проекцией, аудитом и согласием. Прямой EXECUTE нового helper клиентам не выдан. SQL по-прежнему проверяет форму/константы оценки версии, а релевантность и Score вычисляет официальный HTTP API; этот этап не добавляет независимую аттестацию оценки прямого RPC.

## История и проекция

История сравнивает новые факты с прежними нормализованными фактами до обновления проекции. BEFORE UPDATE OF payload фиксирует только изменённые факты; AFTER INSERT создаёт одну начальную запись даже для пустого профиля. BEFORE INSERT не используется: при INSERT ON CONFLICT он сработал бы и на неуспешном пути вставки, создавая лишнюю историю при обновлении.

AFTER INSERT/UPDATE проекция сравнивает нормализованные массивы с NEW.payload. Новые факты, версии, отклики и события пока проецируются из NEW.payload; эта зависимость остаётся открытой. Административные fixture-тесты различают нормализованные данные и OLD.payload и доказывают, что сравнение истории/проекции читает именно таблицы.

## Применение и совместимость

Один DO-блок делает миграцию атомарной и при `psql -f` без внешнего BEGIN. SHARE ROW EXCLUSIVE на пяти таблицах workspace/сущностей и fact_history останавливает записи на время полного preflight и замены функций/триггеров. Административный отчёт должен вернуть ok=true; иначе миграция откатывается. Миграция не переписывает строки и не удаляет данные. Для выпуска всё равно требуется согласованное окно применения и проверка на копии реальной БД.

Порядок: предыдущие зависимые миграции, затем эта миграция, затем приложение с обработкой 503. Откат приложения совместим с новым SQL благодаря сохранённому snapshot/RPC; старая версия может показать общее сообщение ошибки вместо специального 503. Обратная миграция схемы здесь не предлагается. Удаление JSON-массивов потребует отдельного формата хранения, новых входов триггеров, обновлённого checker и проверенного отката.

## Проверки

`supabase/tests/canonical_workspace.sql` проверяет точное число записей истории при INSERT/upsert, неизменённых/изменённых фактах, legacy совместимость, отказ обоих writers без частичных изменений, порядок проверки ревизии, владельцев, сессии и grants. Включены повреждения значений, extra, позиций и скрытой связи.

Synthetic native restore drill подготовлен для девяти SQL-suite на восстановленной и последовательно обновлённой базах PostgreSQL 17. Новая миграция применяется к заполненной базе; manifest сравнивает данные всех 13 таблиц до/после. Перед этим намеренно повреждённая fixture должна остановить миграцию без изменения данных или частично созданного helper. Все fixture-базы удаляются в finally. Факт выполнения и границы локальных проверок записаны в VERIFICATION.md.

Этот этап не оптимизирует частичные DML: полный ограниченный snapshot по-прежнему собирается и сохраняется. Он не закрывает живую приёмку Supabase, многопользовательскую конкуренцию на provider Auth, восстановление копии провайдера или production-выпуск.

В следующей зависимой ветке (docs/EXPLICIT_WORKSPACE_WRITES.md) payload-триггеры удаляются, а сущности/история записываются явно в commit. Описание фаз BEFORE/AFTER выше относится к PR #8; полный JSON mirror сохраняется в обоих этапах. Текущий native drill расширен до десяти SQL-suite и позднего отката миграции.
