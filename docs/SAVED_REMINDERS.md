# Saved tracker tasks (in-app)

This stage follows PR #20 and adds persistent tasks for owned tracker applications. It does not enable a scheduler, email, browser push or calendar API. The existing memory-only ICS draft remains available. The roadmap delivery/permissions/live acceptance item remains open.

## User flow

Open the saved list manually. Create or edit a pending task with title (200 Unicode code points), description (1000), application, named IANA time zone, local minute date (2000–2099), and duration 15/30/60/90 minutes. Check the time, inspect the UTC preview and explicitly accept saving. A nonexistent DST wall time is refused. A repeated time requires choosing an explicit UTC offset. The application link is immutable after creation. All values are plain text; resume/tracker notes are never copied automatically.

Tasks can be completed or cancelled explicitly. These terminal states retain history and cannot be edited/reopened. A separate acknowledged delete removes a task and all its history; the remaining static audit action contains no task text. Up to100 tasks across all statuses; delete/export is explicit. At most48 updates after create leave space for completion/cancellation as event50. No pruning/truncation or implicit cleanup hides history.

Lost writes retain form drafts and block retry until explicit list reload. Reload clears acceptance/time verification even if the revision is unchanged. No mutation is retried automatically. Another tab/workspace update conflicts; reloading preserves the draft for comparison. Leaving the tracker discards the memory-only form. An already submitted request may still commit after navigation; inspect the list on return. History reads do not silently merge workspace state.

Pending/overdue/completed/cancelled/all filters are local. Overdue uses the **server timestamp in the last list response**, not a device clock or live timer; refresh to update it. The list is not a delivery receipt. Past dates are allowed and explicitly visible in preview. ICS export uses the saved task UUID and increasing SEQUENCE, UTC instant/duration and only task title/description; DISPLAY alarm is requested15 minutes earlier. Actual import/update/delivery depends on the user's calendar. No invite is sent. Cancelling/deleting in the app does not cancel an already imported external event; the UI tells the user to remove/update it there.

## Time contract

The accepted local date, named zone, whole-minute UTC offset and UTC instant are all persisted. New writes enumerate all possible whole-minute offsets -14h..+14h with Intl/ISO calendar/h23, so half-hour folds,45-minute zones and skipped dates are covered. Chosen instant is verified by a round trip, not JavaScript's implicit local Date parsing. Node normalizes the zone and derives dueAt; the direct SQL RPC independently checks pg_timezone_names, exact local round trip and numeric offset at that instant. No client can bypass the check by inventing dueAt. Node/PostgreSQL tzdata disagreement fails closed; it never silently adjusts the user's time.

Historical reads validate the accepted local+offset=UTC arithmetic independently of **current** zone rules. Future legal/tzdata changes must not make exports unreadable or rewrite an accepted instant. The UI warns if current rules no longer render the stored local time, and a pending task can be explicitly rechecked/rescheduled. Historical zone names are preserved as text; accepting a new/edited task still requires a currently supported named zone. A UTC instant remains fixed until explicit edit. This does not guarantee future calendar-law predictions.

References checked29Oct2026: PostgreSQL17 [AT TIME ZONE](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-ZONECONVERT), [ambiguous timestamps](https://www.postgresql.org/docs/17/datetime-invalid-input.html), and [ECMAScript402 formatToParts/hour cycles](https://tc39.es/ecma402/2026/). PostgreSQL's implicit ambiguous-time default is deliberately not used to choose an instant.

## Commands, storage and authorization

`20261029095404_saved_reminders.sql` adds reminder_boards (independent owner revision), reminders, reminder_events. Owner/session SELECT RLS; direct client writes and anonymous RPC execution revoked. Foreign-key application ownership and account/workspace/application cascade apply. Export before deletion if history is needed. Private formatter is not executable by clients. Public read/history/command wrappers have empty search_path, explicit live uid/session checks, server UUID/dates and narrow grants; no service-role key in app/client.

Commands share the existing workspace owner/advisory lock, then board/row locks; both workspace and board expected revisions are mandatory. All commands increment board revision once; they do not mutate workspace revision, application status, facts or resume versions. Create/update require SAVE_REMINDER, delete DELETE_REMINDER. Unknown fields/owner/ID/date/created/history on create are rejected. Each accepted non-delete command appends one full immutable-to-clients event snapshot with monotonic sequence. Final snapshot must match the record; schema checks transitions and unchanged fields on terminal events. Server clock moving before a task's previous update fails closed. Task/event/board/audit writes roll back together. SQL administrators can bypass controls; this is not tamper-proof cryptographic history.

`/api/reminders` GET list (max100), GET id owner history (max50 events), GET export=1; POST strict command/owner/revisions with same-origin check, 12KB body cap, active auth/service quota, no-store and no retry. Foreign/missing history IDs return404; owner hints never grant access. API/browser validate arithmetic, owner/revisions and history before rendering. List summaries contain only current task data and event counts, not all history snapshots.

## Export, backup and acceptance

Personal JSON now points to a **fifth** download: reminders/history NDJSON in addition to workspace/audit/consent JSON, fact history, structure and literal versions. Task export captures a board revision/list, reads one validated detail per pull with fresh session/quota check, verifies that revision/content on every detail and rereads the board before complete:true. Concurrent task mutation, missing/corrupt detail, quota/revocation/read failure or64MiB cap yields complete:false. Cancellation discards an in-flight result and stops further reads. The five files do not share one transactional moment. Cancelled/completed tasks are included. Individual history comes from the same owner RPC; account deletion cascades all three tables from the active database, not downloaded/provider copies.

`backup_manifest.py snapshot ... --include-structured` now emits **v5 /19 tables**. Historical v3/15 and v4/16 remain comparable only within their own formats, and cannot be relabeled as a complete v5. Default legacy13 remains historical. Native CI adds fresh/populated/restored SQL suites,20 real concurrent commands, seeds all19 tables, real pg_dump/pg_restore fingerprints, and detects changed reminder history. No real Supabase backup was restored here. The migration was generated with Supabase CLI; production/migration history/real data were not modified. Provider advisors/Auth/PostgREST, actual backup RPO/RTO, live multi-account workflow, operator privacy/retention and real calendar import remain required before activation.

Roll back app code by leaving additive tables/RPCs in place; older code ignores them. Dropping task tables loses user data/history and requires reviewed export/backup and separate authorization. No merge/release or paid infrastructure is authorized by this implementation. External delivery needs explicit channel/recipient consent, secure scheduling, failure/cancellation semantics and live acceptance; none is claimed from task storage alone.
