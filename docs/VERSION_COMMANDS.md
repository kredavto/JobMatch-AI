# Команды версий резюме

Этап зависит от PR #5. Новые команды расширяют существующий RPC `apply_workspace_command`; владелец и активная сессия определяются по JWT, состояние загружается под общей с legacy writer блокировкой. Любой конфликт ревизии отклоняет запись целиком. Ответ — snapshot этой же транзакции с `revision + 1`.

## Сохранение версии

HTTP action version принимает список IDs предложенных правок и необязательный точный templateVersion. Отсутствие значения и ordinary-literal-v1 сохраняют прежний русский протокол без новой метки; ordinary-literal-en-v1 выбирает английские заголовки. Алиасы en/ru, null и неизвестные метки отвергаются. Сервер читает сохранённый профиль, проверяет ревизию и заново выполняет прежние propose/match/matchMetadata. Порядок свидетельств следует ранжированию движка, не порядку запроса. Повторяющиеся IDs правок отклоняются; неизвестные, неподтверждённые и исключённые движком правки не принимаются. Выбор правок не меняет расчёт Score всего сохранённого профиля.

Команда SQL содержит только:

| Поле | Значение |
| --- | --- |
| `action` | `version` |
| `evidence_ids` | До 500 различных строковых ID собственных подтверждённых фактов, 1–100 знаков каждый, в порядке вывода |
| `score` | Целое 0–100 из серверного расчёта |
| `match_metadata` | Текущие правила, веса, вклады, число требований и исходов |
| `template_version` | Необязательно; только `ordinary-literal-en-v1`. Для прежнего русского поведения поле отсутствует |

ID, дата, текст, vacancy, engine_version, profile_revision и evidence_snapshot не принимаются от клиента. SQL создаёт UUID/UTC timestamp, читает vacancy из заблокированного состояния, задаёт rules-v1/текущую ревизию и собирает снимок выбранных фактов в порядке профиля. В текст они попадают в порядке evidence_ids. Английская метка замораживает только RELEVANT EXPERIENCE / PROFILE; обычный русский вариант по-прежнему использует РЕЛЕВАНТНЫЙ ОПЫТ / ПРОФИЛЬ. Исходные строки с теми же trim-текстами удаляются из остатка; прочие строки и порядок сохраняются. При пустом выборе текст точно равен original, включая CRLF и пробелы.

HTTP не передаёт пользовательские score/metadata/text/snapshot/created. Структура RPC строгая: дополнительные поля отклоняются, метаданные должны содержать фиксированные константы текущих правил и согласованные счётчики. SQL не пересчитывает Match Score и не доказывает релевантность: прямой RPC может передать структурно допустимую сводку. Это не серверная аттестация расчёта и не независимая проверка истинности фактов. Score не используется для доступа к данным. При изменении текущих правил потребуется согласованное обновление SQL-контракта и проверок паритета.

Чтение в API нужно для существующего TypeScript-движка; полный workspace обратно на запись не отправляется. Если между read и command кто-то записал новое состояние, SQL возвращает конфликт, не прикрепляя оценку к другой ревизии и не повторяя запись.

## Восстановление

Команда содержит только `action: restore` и `id` сохранённой собственной версии, 1–100 знаков. Прежние строковые ID поддерживаются. Серверу не нужен предварительный read профиля.

SQL копирует сохранённый JSON версии и меняет только ID, created и restored_from. Последнее поле ссылается на непосредственную исходную версию, даже если она сама была восстановлена. Текст, Score, исторические свидетельства, optional/unknown fields и отсутствие старых полей сохраняются точно. Старые версии и привязки откликов не меняются; профиль не заменяется. Восстановление возможно после реимпорта и без текущей vacancy.

## Границы и выпуск

Предел — 100 сохранённых версий для обеих команд. Подмена текста/снимка, неподтверждённый/чужой ID и неверная ревизия не сохраняют частичных изменений, аудита или проекции. Private helper имеет SECURITY INVOKER, пустой search_path и закрыт для public/anon/authenticated. Прежний commit gate дополнительно проверяет переход и текст; snapshot/legacy writer сохранены для отката.

Перед выпуском объединить/принять зависимые PR #4/#5, перепроверить актуальный base, применить все предыдущие миграции и `20261028110003_version_commands.sql`, затем API. При откате кода SQL-расширение можно оставить; снимать его при работающем новом API нельзя. Чистая schema.sql содержит те же стадии. Нужны native PostgreSQL 17 CI и живая приёмка нового RPC перед выпуском. Удаление дублирующих JSON-массивов, legacy RPC и эксплуатационный restore провайдера — отдельные задачи.

## Явный английский шаблон и проверка ответа — PR #44

Миграция `20261030123130_ordinary_english_versions.sql` создана реальной CLI2.122.0 до записи SQL ([bootstrap](https://github.com/kredavto/JobMatch-AI/actions/runs/41055953415)). Она меняет только существующие private.apply_version_intent и private.validate_version_write с прежними сигнатурами/SECURITY INVOKER/empty search_path/закрытыми grants. Новых таблиц/публичных RPC/зависимостей нет. Canonical schema включает тот же SQL; рабочая база не менялась.

Выбор языка заголовков в редакторе отделён от UI locale и по умолчанию сохраняет Russian legacy behavior. Смена UI locale и переход между вкладками сохраняют выбор фактов/шаблона/pending request и не делают запрос. Явное новое чтение без сохранения черновиков и выход из аккаунта сбрасывают выбор к прежнему русскому варианту. Предпросмотр меняется только по явному выбору document template; отдельная кнопка сохраняет показанную версию. При пустом выборе фактов English template также возвращает исходный original без добавления заголовков и нормализации CRLF. Метка в этом случае описывает выбранное правило формирования, а не язык всего исходного документа.

Новая English команда хранит template_version в normalized resume_versions.extra. Исторические/новые default Russian записи не получают метку задним числом. История показывает recorded tag или явно сообщает, что метка не сохранена; язык по содержимому не определяется. Unknown historical tags сохраняются как opaque JSON, а не принимаются за поддержанный новый template: строки отображаются как recorded tag, значения другого типа — как unsupported-format note; JSON export сохраняет исходное значение. Чтение не сужает прежний passthrough контракт. Новая запись с неизвестной/null/неправильной меткой отвергается SQL; compatibility snapshot writer проверяет тот же exact English render. Metadata/история проходят canonical read и backup fingerprint как прежде.

Для нового English save и API, и клиент сверяют ответ с отправленным сохранённым состоянием до установки UI: тот же известный owner, ровно revision+1, единственная добавленная версия, прежние версии/факты/исходники/цель/отклики/unknown fields без изменений, новый UUID/UTC timestamp, точный template/text/evidence order/snapshot/profile revision/engine/score/match metadata. Проверка не использует более поздний draft полей. Подменённый успешный ответ останавливает установку данных и требует чтения; таймаут/потерянный ответ не повторяет запись. Client owner lifecycle дополнительно отвергает поздний результат при смене owner reference. Уже отправленная запись не считается отменённой.

Это проверка exact literal transformation/acknowledgement, не независимая проверка Score, квалификации, смысла или происхождения JWT за пределами провайдера. Ordinary JSON хранит выбранные evidence_snapshot и revision, **не полный original snapshot, не preview hash и не цифровую подпись**; template tag не является серверной аттестацией расчёта. Полное независимое восстановление исторического исходника только по ordinary JSON не заявляется. Текст/метаданные исторической версии читаются как сохранены, а не рендерятся текущим шаблоном. Семантическое/модельное переписывание остаётся открытым.

Restore копирует English tag/text/evidence/extra точно, меняя только id/created/restored_from; ни смена UI, ни текущее содержимое профиля не переводят историю. Shared limit100 для version/restore сохраняется. Клиентские прямые записи таблиц остаются закрыты, workspace command/legacy gate проверяют сохранность прежней истории; администратор может обойти эти ограничения.

После review/deployment approval сначала применяются зависимости и эта миграция, затем новая API/UI. Старый writer, который формирует Russian candidates, можно оставить; при rollback необходимо сохранить passthrough reader/export и новый exact render validator. Откат private.validate_version_write к Russian-only коду при оставшемся English writer недопустим. Не удалять/не переводить English rows ради старого интерфейса. Удаление SQL-расширения требует отдельно проверенного плана совместимости; этот PR не выполняет deployment/merge/release.

Structured-v6/21 tables и шесть user archive files сохраняются. Native synthetic restore добавляет отдельного тестового owner с RU/EN ordinary rows, читает English после pg_restore и обнаруживает отдельную подмену template_version в extra. Fixtures не являются production seed, реальной Supabase копией или RPO/RTO proof.
