# Команды версий резюме

Этап зависит от PR #5. Новые команды расширяют существующий RPC `apply_workspace_command`; владелец и активная сессия определяются по JWT, состояние загружается под общей с legacy writer блокировкой. Любой конфликт ревизии отклоняет запись целиком. Ответ — snapshot этой же транзакции с `revision + 1`.

## Сохранение версии

HTTP action version принимает список IDs предложенных правок. Сервер читает сохранённый профиль, проверяет ревизию и заново выполняет прежние propose/match/matchMetadata. Порядок свидетельств следует ранжированию движка, не порядку запроса. Повторяющиеся IDs правок отклоняются; неизвестные, неподтверждённые и исключённые движком правки не принимаются. Выбор правок не меняет расчёт Score всего сохранённого профиля.

Команда SQL содержит только:

| Поле | Значение |
| --- | --- |
| `action` | `version` |
| `evidence_ids` | До 500 различных строковых ID собственных подтверждённых фактов, 1–100 знаков каждый, в порядке вывода |
| `score` | Целое 0–100 из серверного расчёта |
| `match_metadata` | Текущие правила, веса, вклады, число требований и исходов |

ID, дата, текст, vacancy, engine_version, profile_revision и evidence_snapshot не принимаются от клиента. SQL создаёт UUID/UTC timestamp, читает vacancy из заблокированного состояния, задаёт rules-v1/текущую ревизию и собирает снимок выбранных фактов в порядке профиля. В текст они попадают в порядке evidence_ids. Исходные строки с теми же trim-текстами удаляются из остатка; прочие строки и порядок сохраняются. При пустом выборе текст точно равен original, включая CRLF и пробелы.

HTTP не передаёт пользовательские score/metadata/text/snapshot/created. Структура RPC строгая: дополнительные поля отклоняются, метаданные должны содержать фиксированные константы текущих правил и согласованные счётчики. SQL не пересчитывает Match Score и не доказывает релевантность: прямой RPC может передать структурно допустимую сводку. Это не серверная аттестация расчёта и не независимая проверка истинности фактов. Score не используется для доступа к данным. При изменении текущих правил потребуется согласованное обновление SQL-контракта и проверок паритета.

Чтение в API нужно для существующего TypeScript-движка; полный workspace обратно на запись не отправляется. Если между read и command кто-то записал новое состояние, SQL возвращает конфликт, не прикрепляя оценку к другой ревизии и не повторяя запись.

## Восстановление

Команда содержит только `action: restore` и `id` сохранённой собственной версии, 1–100 знаков. Прежние строковые ID поддерживаются. Серверу не нужен предварительный read профиля.

SQL копирует сохранённый JSON версии и меняет только ID, created и restored_from. Последнее поле ссылается на непосредственную исходную версию, даже если она сама была восстановлена. Текст, Score, исторические свидетельства, optional/unknown fields и отсутствие старых полей сохраняются точно. Старые версии и привязки откликов не меняются; профиль не заменяется. Восстановление возможно после реимпорта и без текущей vacancy.

## Границы и выпуск

Предел — 100 сохранённых версий для обеих команд. Подмена текста/снимка, неподтверждённый/чужой ID и неверная ревизия не сохраняют частичных изменений, аудита или проекции. Private helper имеет SECURITY INVOKER, пустой search_path и закрыт для public/anon/authenticated. Прежний commit gate дополнительно проверяет переход и текст; snapshot/legacy writer сохранены для отката.

Перед выпуском объединить/принять зависимые PR #4/#5, перепроверить актуальный base, применить все предыдущие миграции и `20261028110003_version_commands.sql`, затем API. При откате кода SQL-расширение можно оставить; снимать его при работающем новом API нельзя. Чистая schema.sql содержит те же стадии. Нужны native PostgreSQL 17 CI и живая приёмка нового RPC перед выпуском. Удаление дублирующих JSON-массивов, legacy RPC и эксплуатационный restore провайдера — отдельные задачи.
