# Явная транзакционная запись workspace

Этап зависит от PR #8. Миграция `20261028110006_explicit_workspace_writes.sql` переносит запись сущностей и истории из payload-триггеров в существующую `private.commit_workspace`. Контракты `save_workspace`, `apply_workspace_command`, `read_workspace` и HTTP API сохраняются. Полный JSON mirror пока остаётся.

## Последовательность записи

Оба RPC используют одну границу записи:

1. Проверить активную сессию/владельца, взять транзакционную advisory-блокировку и FOR UPDATE, проверить ревизию и паритет через `private.locked_workspace` из PR #8.
2. Проверить допустимые изменения и свидетельства прежними validate-функциями.
3. Создать/обновить строку workspace с новой ревизией и полным совместимым snapshot. Строка нужна как FK-родитель сущностей.
4. Передать проверенное новое состояние явно в закрытую `private.project_workspace`. Сохранение сущностей больше не читает NEW.payload и не перечитывает сохранённый JSON как вход записи.
5. Добавить историю при фактическом создании workspace или изменении фактов. Для существующего workspace с revision=0 начальная история повторно не создаётся только из-за нулевой ревизии. Значения снимка берутся из проверенного аргумента.
6. Добавить аудит и согласие в той же транзакции.
7. Повторно проверить паритет/структуру и совпадение сохранённого состояния с проверенным новым состоянием. Любое расхождение, включая изменение скаляров, останавливает запись.

Ошибки на любом шаге откатывают workspace/ревизию, сущности, историю, аудит и согласие. PostgreSQL sequences могут оставлять пропуски после rollback; непрерывность ID истории не обещается. Сохраняются CONFLICT для старой ревизии, INVALID_WRITE для неверного изменения, AUTH для неактивной сессии и безопасный HTTP 503 при PROJECTION_CONFLICT. Автоматического repair, retry, fallback и пользовательского флага обхода нет.

Удаляются три триггера `workspace_capture_facts`, `workspace_capture_initial_facts`, `workspace_sync_entities` и две больше не используемые trigger-функции. Новых функций/RPC/таблиц/ролей нет; прямые клиентские записи в workspace, сущности, историю, аудит и согласие остаются запрещены. Внутренний projector и validate-функции клиентам не открываются.

## Совместимость и административные операции

Старые клиенты продолжают использовать save_workspace с теми же ревизиями и правилами. Откат приложения совместим с новым SQL и сохранённым полным JSON snapshot; обратная миграция SQL для отката приложения не нужна. Main/production этим локальным этапом не меняются.

Прямой административный INSERT/UPDATE workspaces больше не создаёт сущности/историю автоматически. Такие операции всегда обходили валидированную RPC-границу; при обслуживании требуется явно согласованная транзакция и проверка паритета, а не редактирование одного mirror. Неполная ручная запись будет обнаружена следующей RPC-записью. Production-кода автоматического исправления нет.

Синтетические исторические fixtures теперь явно заполняют сущности/историю. `restore_seed.sql` работает и до, и после миграции: на старой схеме выполняются старые триггеры, на новой — явная fixture-инициализация. Это ветвление есть только в тестовом seed, не в production writer.

## Миграция

Один атомарный DO-блок под SHARE ROW EXCLUSIVE на workspace, четырёх таблицах сущностей и fact_history выполняет полный административный preflight, заменяет commit и удаляет триггеры/функции. В миграции нет DML/backfill, изменения строк, удаления массивов или прав клиента. Ошибка preflight либо поздняя ошибка DDL откатывает весь блок.

Применять после зависимых миграций PR #4–#8, в согласованном окне остановки всех writers. Перед реальным выпуском нужна проверка на копии целевой БД. Возврат SQL-реализации к PR #8 потребует точных прежних определений под теми же блокировками и preflight; отдельная готовая обратная миграция этим этапом не предлагается.

## Проверки и оставшаяся работа

Новая SQL-suite `explicit_workspace_writes.sql` проверяет ошибки на четырёх шагах для обоих writers и нового/существующего workspace, начальную/неизменную историю, отсутствие старых triggers/functions и изоляцию владельцев. Искусственная порча mirror на BEFORE INSERT доказывает, что projector получает проверенный аргумент: запись факта доходит до контролируемого отказа в profile_facts даже без массивов в NEW.payload. Отдельно порча массивов/скаляра проверяет финальную границу целостности. Все probes откатываются.

Десять SQL-suite проверяются при clean install и обновлении заполненной базы; данные всех 13 fixture-таблиц сравниваются до/после миграции. Проверяются ранний отказ при расхождении и поздний отказ после удаления триггеров с восстановлением прежних строк, функций/grants и триггеров. Native PostgreSQL 17 restore drill подготовлен для тех же сценариев; фактические результаты и ограничения приведены в VERIFICATION.md.

Полные bounded JSON состояния всё ещё строятся в памяти и сохраняются в mirror. Этот этап не вводит частичные DML и не уменьшает хранимые данные. До удаления массивов нужны новый режим хранения/checker, связанный с cutover preflight, план и проверка rollback, а также испытания конкурентных writers. Synthetic Auth не заменяет живую приёмку Supabase и восстановление копии провайдера.

## Проверка конкурентных writers

`scripts/check_workspace_concurrency.py` запускается native restore drill в восстановленной и последовательно обновлённой базах. Он допускает только явно включённый локальный/CI PostgreSQL и имя generated disposable базы jobmatch_drill_<32 hex>; PG service/host override запрещены. Auth fixture синтетический, внешние аккаунты/письма не создаются.

Два независимых psql-соединения под authenticated одновременно вызывают command/legacy с одной ревизией для нового, затем существующего workspace. До освобождения общей owner-блокировки probe наблюдает реальные ungranted advisory locks через pg_locks. Требуются ровно один OK и один CONFLICT, одна новая ревизия/аудит, неизменная история фактов и отсутствие частичных данных. Порядок победителей не фиксируется.

Отдельно здоровый владелец завершает запись до освобождения блокировки другого владельца. Два ожидающих writer после удаления синтетической Auth session обязаны получить AUTH без новой ревизии/аудита/истории. ACCESS EXCLUSIVE gate на workspaces с preflight подтверждается реальным ожиданием relation lock; writer продолжает только после снятия gate. Это модель будущего окна cutover, а не применение миграции удаления массивов.

Готовность holder подтверждается bounded handshake, ожидание блокировок — опросом каталога с deadline. На соединениях установлены statement/lock/idle transaction timeout; клиентские процессы также ограничены тайм-аутами. При успехе/ошибке закрываются процессы и каскадно удаляются временные Auth users; базами дополнительно управляет finally основного drill. Успех не печатается до успешной очистки. В выводе только фиксированные статусы/названия этапов, без SQL, строк или параметров подключения.

Семь unit-проверок подтверждают guard, строгий worker protocol, отказ без подключения, очистку после timeout и отсутствие ложного успеха/секретов при ошибке очистки. Они не подменяют реальные гонки: фактический native результат — в VERIFICATION.md. Эти сценарии не являются нагрузочным тестом или проверкой реального Supabase Auth.

В следующей зависимой compact-ветке (docs/COMPACT_WORKSPACE_STORAGE.md) stored mirror удаляется под атомарным gate, а полный RPC-ответ собирается из таблиц. Настоящий документ описывает mirror-фазу PR #9; legacy RPC и явный вход projector сохраняются и после перехода.
