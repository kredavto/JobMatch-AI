# Foreground reminder notifications

This candidate extends the current saved-reminder tracker, stacked on ready/unmerged PR #118. It is a bounded **visible open-tab** mode, not background push or a scheduler. The server continues to return `delivery: none`: no server delivery, queue, subscription, delivery receipt or mutation is introduced. Existing API/SQL write permissions stay default off.

## Consent and lifecycle

No notification permission prompt or automatic reminder read occurs on mount, manual snapshot load, language switch or application-section navigation. A loaded owner-bound snapshot, a separate checkbox and an explicit enable button are required. Browser permission is requested directly in that user action. Existing granted browser permission still requires the tab checkbox/button. App opt-in and attempted-show ledger exist only in owner-keyed tab memory; sign-out/unmount/reload clears them. Browser permission is revoked separately in browser settings.

While opted in, the visible document checks `/api/reminders?expectedOwnerId=…` every 30 seconds, with the owner header, authenticated same-origin request, existing server quota/session validation and `no-store`. No POST or delivery mutation is sent. Busy/current write/read guards suppress checks; hidden documents abort reads. Pause, error, page exit, withdrawal or sign-out stops checks and closes the tab's notification handle. Permission refusal/revocation does not automatically retry. A pending permission/read answer cannot revive stopped consent. A bounded server read failure stops checks; protocol/session failures require explicit combined workspace/reminder read before enabling again. Browser-local show failure is also shown with fixed copy, without private error details.

Every show requires a **fresh** schema-valid owner snapshot. Lower revisions or differing same-revision snapshots refuse. A ref to the current confirmed state and synchronous pending-request guard prevent an older background response from replacing a concurrent foreground ACK. Fresh reads update the loaded tracker without changing a local form: external changes still require explicit compare. The response can become stale after the server read; this is not an atomic transaction with an OS notification. An external cancellation is reconciled at the next permitted read, not instantly or while the page is hidden/closed.

## Timing, privacy and honest evidence

Only scheduled saved instants at or after activation are eligible. Future instants and already overdue tasks at activation are excluded. The catch-up window is at most five minutes. Nonfinite/backward clocks stop checks. The in-memory `(record ID, saved dueAt)` ledger suppresses repeat requests across unrelated row revisions; a newly rescheduled instant is separate. It is bounded at 1,000 attempts, with expiry pruning; it is not durable or cross-tab exactly-once delivery. At most one generic notification is requested per due batch, replacing the previous tab handle.

Only localized generic JobMatch AI title/body, a random tab tag and language reach the OS API. No vacancy, resume, description, application/reminder/owner ID appears in that payload. Clicking focuses this window. Cancellation/completion/deletion/rescheduling removes old active keys on the next known snapshot; stopping/signing out closes the handle best-effort. OS/browser behavior may differ. The counter measures successful constructor requests; neither that counter nor `onshow` would prove physical delivery. Browser errors stop checks; no automatic replay is scheduled. Hidden/closed-tab/background, mobile/PWA, screen-reader and real device delivery remain unaccepted. No real user's notification is generated by CI.

Tests distinguish synthetic permission/visibility/error injections from an actual hosted Chromium `Notification` constructor with an explicit test permission grant. Both use public synthetic records and the actual current Root, no production account. Neither is physical-device acceptance.

Standards consulted 2026-11-05: [WHATWG Notifications](https://notifications.spec.whatwg.org/) and [permission user gesture/secure context](https://developer.mozilla.org/en-US/docs/Web/API/Notification/requestPermission_static). No service worker, cache scope, browser push subscription, mail/calendar integration, dependency, production configuration or database migration changes.

Accepted candidate evidence: [PR #119 source results](VERIFICATION_FOREGROUND_REMINDERS_20261105.md). The pinned default headless-shell/incognito context returns denied despite a test override; this is a negative case. A separate full new-headless Chromium regular temporary profile exercises the original native constructor with a test grant, without replacing the API. Both are automated observations, not real-device delivery or human prompt acceptance. The owned temporary profile is always removed.
