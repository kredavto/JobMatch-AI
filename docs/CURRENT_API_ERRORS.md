# Current API error codes and RU/EN preparation

This additive block follows #90, adapting the design of #22 to current compact storage, source profiles/versions, saved letters, parser/TLS/OCR and signed Auth quota. It does not enable an incomplete English UI. RU remains the released language; full screen/date/offline localization and language switching remain OPEN.

`failure` emits `{error,code}` from the closed `lib/i18n/api-errors.ts` catalog.121 codes have RU/EN copy and permitted status. `UserError.code` is typed; all131 current production constructor sites were reviewed and assigned explicit codes. Fixed AUTH/ORIGIN/CONFLICT/RATE control tags retain401/403/409/429. Zod/JSON syntax errors become INVALID_INPUT400, unexpected errors INTERNAL_ERROR500. Uncoded/unknown/status-mismatched UserError gets REQUEST_FAILED with a valid400–599 status (invalid status clamps500). Catalog copy replaces exception text even for recognized codes. No raw SQL/Auth/provider diagnostic, user input, exception stack/cause or configured origin is serialized by this boundary. Mail-origin exception still supports internal callers; public copy directs the user to the main application without echoing configuration.

HTTP status remains authoritative; codes do not grant access, attest identity/consent/write outcome, or authorize retry. No-store and Retry-After60 for429 remain. Success payloads, cookies, ownership, revision/CAS/ack guards, quotas, flags, SQL and permission contracts are unchanged. HH_IMPORT_* and AUTH_PROTECTION_UNAVAILABLE identifiers already used internally are preserved in the closed catalog. HH stays disabled/preview-only; no storage permission or HH write was added.

Exception: the public import endpoint retains its strict existing `{code:'OCR_LIMIT'}`400 shape, required by current PDF clients. It now chooses this shape by validated PARSER_OCR_LIMIT+status400, never Russian wording. Private worker protocol INVALID/TOO_LARGE/TIMEOUT/OCR_LIMIT/BUSY/UNAVAILABLE is unchanged; parser forwarding checks the explicit public code and corresponding status. A transport error that only resembles Russian BUSY/OCR copy cannot authorize forwarding or an OCR claim. No inline fallback/retry was added.

`requestJson`/workspace/auth validators accept explicit RU/EN for future integration. A recognized code+matching status renders only fixed catalog copy. Unknown/prototype/malformed/mismatched codes become CLIENT_INVALID_RESPONSE while retaining the actual HTTP status; a body cannot turn409 into401. Caller cancellation remains combined with the existing30s timeout. Lost mutation remains status0/CLIENT_NETWORK_LOST and explicitly unknown; no replay. Existing panels that intentionally use fixed status-only copy retain their guards and do not activate English.

Limited compatibility: old **same-origin** code-less responses may display a nonempty own `error` string in RU only, at most2000UTF16 units and no binary controls. Inherited/invalid/oversized text is rejected; EN always uses a fixed fallback. This legacy trust path is not a guarantee to redact arbitrary text from an old server. Current coded responses never use that field as display authority. Remove compatibility only through an explicit client/server transition.
