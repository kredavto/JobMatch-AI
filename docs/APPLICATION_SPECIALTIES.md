## Product contract

A specialty is an optional **label entered by the user for one saved application**. It is not extracted from a vacancy title, resume, search goal, confirmed fact or external taxonomy. Adding/changing it does not verify a qualification, call a model/hh.ru, affect Match Score, change a status/event, or enter resume/letter text.

The label is literal and case-sensitive: no Unicode normalization, case folding, translation or inferred grouping. New values must be well-formed Unicode strings of at most120 code points, without leading/trailing ECMAScript trim whitespace or C0/C1 control characters. Empty string explicitly clears the classification. UI uses a240 UTF-16 input limit plus the actual120-code-point validation, so astral characters are not counted as two code points. Invalid input is never silently trimmed/truncated/coerced into a write.

Existing conforming string-valued specialty metadata is recognized verbatim. Absent or malformed values are unclassified. Unknown pre-existing specialty JSON is preserved on reads and unrelated writes. It is unclassified and displays a fixed explanatory notice, not the opaque value. The user may replace/clear it explicitly. No migration invents labels for old applications or copies the current search goal into historical records.

## Write and compatibility contract

The existing application command accepts optional `specialty`; user/session/owner/revision/quota gates remain in force. Omission preserves presence/value on updates. New/changed values pass the same SQL/TypeScript constraints. Empty string clears; removing a previously present property in a compatibility snapshot refuses the entire transaction. Unchanged legacy unknown values remain valid round trips.

The additive migration `supabase/migrations/20261031084309_application_specialties.sql` replaces only the private application validator/state transformer and adds a private immutable predicate. It does not rewrite rows, add a table/column/index, grant new privileges or replace the guarded public RPC. Existing canonical `public.applications.extra` stores the field, and the current21-table backup manifest already hashes it. Private functions are SECURITY INVOKER, have empty search_path and no PUBLIC/anon/authenticated execute. Public owner/session RPC, RLS, revision locking and atomic audit handling are unchanged. No new public endpoint or admin API exists.

Frontend writes require a known owner and a distinct Save click. A shared synchronous tracker guard blocks duplicate requests. The acknowledgement must match the submitted owner, revision+1, row ID and entire previous workspace except the explicit label. Foreign owner, missing/wrong label, revision gap, changed note/status/source/other row or malformed response is rejected before installation; state/draft remain and ambiguous results require a manual reload. There is no retry/fallback.

Drafts live in parent memory, survive filter/tab/language changes, and are cleared on logout/delete. A late acknowledgement removes only its submitted text; newer typing remains with the newly saved base. A different editing context or failed write never clears a draft. Unsaved notes survive label writes. No local storage of labels/drafts is added.

## Analytics and export

The specialty filter combines with the existing date/version filters, including previous-period comparisons and unplaced-time notices. It uses current explicit labels; changing a label moves the whole application and its recorded history. This does not reconstruct a specialty as it existed when submitted. Stale unavailable selections remain explicit rather than appearing as All.

Old/empty/unrecognized labels remain in an unclassified group. Labels resembling internal sentinels stay distinct from that group. Groups show total selected, sent, explicit invitations, interview/offer observations, explicit offers, responses, and rates with sent denominators. A repeated status counts once per application. A later stage does not imply earlier stages. Planned records remain in total, not in a fabricated sent denominator; no sent observations means a null rate.

Status history is manual and may be incomplete; recent applications had less time to get a response. Group size/rate differences do not establish causal effects of resumes or specialties. RU/EN copy states these limits.

`jobmatch-specialties.csv` is a separate summary with9 localized columns; literal labels/Unicode survive, formula prefixes are escaped and quotes doubled. Existing application/monthly CSV formats, frozen resume templates and ordinary/structured version provenance remain unchanged. Personal JSON/workspace export retains the optional metadata through the existing owner-only contract. Tracker search can find saved labels, while grouping itself stays literal.
