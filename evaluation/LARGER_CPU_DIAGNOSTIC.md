# Separate 7B CPU diagnostic

This experiment tests a third reviewed public model on the **unchanged** 28 linker and 12 profile synthetic cases. It does not compare scores causally to the previous 4 GiB jobs, accept a model, activate a deployment or process user data. The prior two-model comparison continues to require exactly its two original pins.

The official [Qwen2.5-7B-Instruct-GGUF immutable repository](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-GGUF/tree/bb5d59e06d9551d752d08b292a50eb208b07ab1f) provides a single `qwen2.5-7b-instruct-q3_k_m.gguf`: 3808391072 bytes, SHA256 `a96b16179dc6cc9afdf0cf7a96a80c199cbd00b9be207c3465be21cb721cca5e`. The immutable LFS pointer and Apache-2.0 LICENSE are verified before download; the actual stream must match both size and digest. LICENSE SHA256 is `832dd9e00a68dd83b3c3fb9f5588dad7dcf337a0db50f7d9483f310cd292e92e`. This is a different parameter count **and** quantization from the old Q8 models; no isolated size/quantization effect is claimed.

`fetch_cpu_model.py --larger <new-directory>` and exact slot `larger` select this literal manifest, never a caller URL/revision/resource override. Unknown slots, changed pins, incorrect pointers/licenses/weights, redirects outside the fixed public HTTPS allowlist, deadlines and existing destinations refuse. Existing destinations are preserved. The launcher checks the read-only file before and after execution and starts the owned process itself. This binds local execution to a verified file, not remote cryptographic attestation.

The separate workflow uses a standard public `ubuntu-24.04` runner only. [GitHub documents 4 CPU/16 GB RAM/14 GB storage](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) and [free standard public runners](https://docs.github.com/en/billing/concepts/product-billing/github-actions). No larger/self-hosted/GPU runner, registry push, model cache or artifact upload is configured. Before download a read-only preflight requires at least 12 GiB available disk on `RUNNER_TEMP` (the actual model destination filesystem) and total physical RAM; failure stops, without deleting installed tools/data or substituting paid capacity. Capacity is checked, not guaranteed by the documentation alone. Docker build/storage/startup may still fail and must be recorded as such.

Two sequential containers use one built image/binary, each `--network none --read-only --cap-drop ALL --security-opt no-new-privileges`, 4 CPU/8 GiB/128 PIDs/64 MiB tmpfs, uid1000, model and code read-only, fixed loopback server and 900-second outer deadline. Context4096/threads4/seed42/temperature0/maxTokens2048 and fixed case source/gold/order/20-second deadlines are retained. PR #57 used profile grammar v1; candidate #58 emits source-specific v2 grammar with the same prompt text and corpora, explicitly versioned in its separate report. The two versions remain separate experiments. A different model tokenizer can still exceed context; transport limits and complete-response checks are not relaxed. One task's owned process cannot retain conversational state for the next task.

Each existing producer emits its original safe V4 linker or V1 profile report, including actual usage/stop/failure counts, corpus/prompt hashes and per-case grades/stages, with no raw completions. Scripted tests validate the whitelist/loader/guards and are never actual-model evidence. Quality failure can produce a completed negative diagnostic; green CI is not acceptance. A transport-incomplete diagnostic must remain incomplete, not a successful 40-response claim. Production model/profile switches remain off; `acceptance=not-accepted`, remote identity/independent held-out/semantic acceptance remain unverified. Actual results belong in a separate immutable execution archive once the job has run.
