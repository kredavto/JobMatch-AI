## Same execution controls

The public standard `ubuntu-24.04` job builds llama.cpp `8642541b255bfb5dc39cd351a178be09013a55d6` once and runs both models sequentially using the resulting immutable Docker image ID. Each inference container has network none, read-only repository/root/model, uid1000, dropped capabilities/no-new-privileges,4CPU/4GiB/128PIDs,64MiB noexec tmpfs and a900s external deadline. No GPU/larger runner, paid provisioning, remote inference, model cache/artifact upload or registry push is introduced. The [standard public runner terms](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) were checked for the current public repository; this does not guarantee future billing after repository/runner changes.

The corpus, gold, source-lines-v1 prompt/grammar, eligible-fact filtering, validation/grading, context4096, threads4, temperature0, maxTokens2048, seed42, private loopback and finite request multiplicity stay fixed. Model identity/alias is the intended independent variable. The transport never reads gold, repairs a response, substitutes a result or retries. No application feature is enabled by this job. Provider/model acceptance remains false even for28 exact-gold passes.

## Report verification and privacy

Each producer retains the existing `JOBMATCH_CPU_DIAGNOSTIC_V4` format. A new CI-only comparison requires exactly eight ordered phase markers plus one complete V4 JSON report from each private job-owned file. The reports must identify the distinct reviewed pins, exact license/corpus/prompt contracts, complete28/28 cases and28 accepted requests. The complete-comparison path additionally requires28 validated actual backend responses, positive per-response-bounded generated tokens,28 coherent stop/length results and zero transport/rejected requests. Case order, IDs/languages/categories, grade/pass/error/quality/exit codes, failure stages and link-audit coverage must agree. Provider contract errors and gold mismatches remain visible, not successful grades.

Both reports must describe the same image/binary/Node/architecture/CPU and non-overlapping sequential timestamps. This is **workflow execution binding and reported consistency, not remote attestation**. Mutable base image/apt/compiler inputs do not establish bit-reproducible builds or future quality reproducibility. Only one run per model is measured, without randomization or statistical inference; chronological/order and machine effects are not eliminated.

The CLI accepts no arguments and only the approved public CI/test context, numeric workflow run ID, and an exclusive private real directory immediately below RUNNER_TEMP with a fixed generated name. Files must be owned regular single-link private bounded files; symlinks, FIFOs/devices, invalid UTF-8, partial/extra/missing phases and changes during bounded reads are refused. O_NONBLOCK prevents a FIFO from blocking before file validation. Refusals print no supplied paths/values or raw diagnostics. Output contains reviewed public pins, hashes, fixed corpus labels/counters/durations, runtime version and a CPU-description hash, not raw CPU/provider/model text. Owned temporary models/logs are removed after the job; pre-existing user directories are not cleanup targets.

`JOBMATCH_CPU_COMPARISON_V1` always says acceptance=not-accepted, independentHeldOut=not-performed, remoteAttestation=not-performed and deploymentIdentityVerified=false. A green job confirms completed coherent diagnostics, not an accepted model. Known synthetic exact gold, source-vocabulary constraints, no semantic adjudication, no representative held-out set and no production acceptance are explicit limitations. No SMTP/hh.ru/provider DB/user-data operation is performed.

Docs-only final commits explicitly skip both weight downloads, the build, both model runs and the comparison; the immutable executable commit/run/report remains the actual evidence. Unit fixtures and a skipped final run cannot replace it.

## A failed backend attempt is not a complete comparison

The first actual run on `5be5a2af964ce7da28a48ba5cbd1f78180bff58e` completed both evaluator loops, but the1.5B producer had27 validated backend responses/1 failure. The strict comparison correctly refused, and that failed CI run is retained. The failing request duration was19504ms beside the unchanged19500ms bridge deadline. Raw upstream diagnostics were deliberately not logged, so this observation is not proof of a specific native upstream error or timeout cause. No request/input/limit/gold changes or response repairs were made to obtain a more favorable outcome.

A separate `assessCpuComparison` path now distinguishes a **coherent completed experiment with an unsuccessful backend request** from malformed/incomplete evidence. It still requires both complete28-case evaluator loops, positive bounded real-response counters, exact known pins/source contracts and equal reported controls/sequential timestamps. Validated responses plus recorded backend failures must equal28; stop/length counts must match validated responses; positive per-response token bounds and enough operational-error rows are required. A citation or gold mismatch cannot substitute for a missing backend request. Zero-response runs, inconsistent counters, altered provenance or missing/truncated evidence fail closed.

For this outcome, `compareCpuReports` still refuses. The CLI emits **JOBMATCH_CPU_COMPARISON_ATTEMPT_V1 / jobmatch-cpu-comparison-attempt-v1**, comparisonStatus=not-comparable, operationalComparisonComplete=false, reason=incomplete-backend-responses, no deltas and acceptance=not-accepted. It does **not** emit the complete COMPARISON_V1 envelope. Exit0 here means a valid negative diagnostic record, not a full operational comparison or accepted model. Invalid/unsupported/incomplete evidence still exits2 without a report. A full COMPARISON_V1 remains available only when both strict complete-response gates pass. Both the original refusal and subsequent code-validation run are archived, not selected by a favorable score.
